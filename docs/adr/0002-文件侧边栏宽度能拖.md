# 文件侧边栏的宽度能拖，触屏上滑出来铺满

原来这一列的宽度是写死的（`media/chat.css` 里一个 CSS 变量，320px）：宽窗口里常驻多宽、窄窗口里
滑出来多宽，都是它一个数。窄窗口上滑出来的时候右边还漏着一条边——那条边是遮罩，点它就能收起来。
现在拆成两件事：**宽窗口里那条分隔线能拖着改宽度**，拖出来的数记在这台设备上；**触屏（手机、平板）上
滑出来直接铺满整屏**，收起靠这一列头上那颗叉。

没拖过的时候这一列是 360px（原来写死的那个数是 320px），拖起来夹在 300～1200px 之间；
常驻时最宽还要跟「窗口宽度 − 360」取小，给对话那边留得住。

拖的时候只动这一列自己：它浮在对话上面（`position: fixed`），动它不碰版面；对话让出多宽由版面上
那块占位决定，那块先冻着，松手那一下才落定、对话跟着排一次。为什么不做成「拖一路、对话跟着排
一路」：整屏消息重新排字的花销跟会话长度成正比，量过——250 条约 20 毫秒、500 条约 39 毫秒、
1250 条约 74 毫秒，对着 60 帧（约 17 毫秒）那条线看，长会话拖起来会一顿一顿的。
代价是拖动过程中往窄拖会露出一条空档（对话还没跟着往左挪）、往宽拖会暂时压住对话左边一块，
都是拖动中才有，松手就没了。

常驻的门槛（1200px）没动，还是「够宽就常驻在左边、对话让出一块」。右边那一列（项目与会话侧边栏）
一个字没动，还是写死的 320px、门槛 900px——两块不是一回事，这次不去动它。

「触屏」用的是界面上现成的那个判断（`media/chat.js` 里那颗 `IS_TOUCH_DEVICE`：
`(hover: none) and (pointer: coarse)`，意思就是「主输入方式是触摸」），跟「切会话之后要不要自动聚焦
输入框」用的是同一个。带触摸屏的笔记本一般不算触屏（它的主输入还是鼠标），所以那些机器上不会莫名
其妙铺满。

## 备选与代价

- 备选一：给几档固定宽度（窄 / 中 / 宽），点一下切换。放弃了——想一眼看全一个长目录、跟只想瞄一眼
  某个文件，需要的宽度差得很远，几档不够用；而且还得再记一个「现在是第几档」。
- 备选二：宽度挪到设置浮层里填数字。放弃了——改宽度是个得看着结果调的事，填数字要来回开浮层，
  改的时候还看不到改完什么样。
- 备选三：另外画一条看得见的分割条 / 把手。放弃了——左右之间本来就有一条分隔线（面板自己的右边框，
  见 `chat.css` 里 `#filePanel` 那一段），拿它当把手不用多画东西，指针移上去时把那条线点亮就够了。
- 备选四：双击那条线回到默认宽度。放弃了——上下限两头都封死了（最窄 300、最宽 1200，太宽还会跟着
  窗口收），拖不出去也拖不到找不着，不值得为它多一个手势。
- 备选五：手机上也给拖。放弃了——手机上就那点地方，「铺满」和「不铺满」两种就够用了，多一个拖拽
  热区反而跟这一列里的滚动打架。
- 备选六：手机铺满时留一条窄边，把「点外面收起」保住。放弃了——留了边那条缝在手机上点起来费劲，
  而且滑出来的东西本来就是要盖住对话的。
- 备选七：拖动时让对话也跟着重排（拖到哪排到哪）。做了一版、量完放弃了——长会话一帧要几十毫秒
  （数字见上），换来的只是「拖动中就能看到对话的新宽度」，不划算。
- 代价：铺满之后底下那层遮罩整个被盖住，**「点外面收起」在手机上这条路上就没了**，只剩这一列头上
  那颗叉（原来手机上点一下空白处就能收）。
- 代价：多一个记在本机上的值（`pichat.fileSidebarWidth`）。跟这个界面上别的选择一样，它只跟着这一台
  设备、这一个浏览器走：换台机器、换个浏览器要重调。
- 代价：多一套拖拽代码（指针事件、拖动中的光标和选中屏蔽）。仓库里原来没有这种东西可以抄，
  跟「宽度写死」比是多出来的一块。
- 代价：最宽能到 1200px，而这一列里还是那一排标签加一列清单，没为很宽的宽度另外长一套版式，
  所以拖得很宽的时候右边会空掉一片。这是有意的：不为一个能拖的宽度再养一套排版。
- 代价：上限跟着窗口走（`min(1200, 窗口宽度 − 360)`），所以同一个值在不同窗口下看到的宽度可能不一样
  ——在 1300px 的窗口里拖到顶是 940，换到 1600px 的窗口上还是你上次拖的那个数（存的原值没被窗口改掉）。
