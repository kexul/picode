# 浏览器页面自己读文件，不再依赖编辑器

从浏览器页面里点消息流中的文件链接（`src/foo.ts:42` 这种）时，以前是把请求转给一个"打开着这个目录的
VS Code 窗口"去开文件；一个窗口都没开（只用手机、或者只跑了 pichat 没开编辑器）就什么都看不到。
现在改成：后端自己按会话目录把文件读出来，用一个只读地址给页面，界面在浏览器页面左边长出一列
**文件侧边栏**（宽窗口常驻、窄窗口滑入）。插件里的对话面板照旧把文件交给编辑器打开——那边编辑器就在
旁边，本来就好用。

文件接口只看得到**当前会话目录里的文件**（相对路径按会话目录解，路径归一化后要确认真的落在目录内），
目录之外一律提示看不了。这是有意的边界：能打开这个页面的人本来就能让 pi 读这台机器上任何文件，
但"按路径直接取文件"这条路不跟着变成整台机器的读接口。列表里的路径按两档找：先按会话目录拼，
拼不到再在这个会话碰过的文件（read/edit/write 过的）里按文件名匹配。

## 备选与代价

- 备选一：沿用图片那套（页面发一条请求，内容从推送通道发回来）。放弃了——图片是几百 KB、偶尔一次，
  文件可能好几 MB，那条推送通道有积压上限，而且内容要发给连着同一份会话的每一块屏。
- 备选二：让 VS Code 窗口读、把内容回给浏览器页面。放弃了——这正是要摆脱的依赖。
- 备选三：插件面板里也长这一列。放弃了——插件里点链接开编辑器更好用，那块地方也窄。
- 代价：多一个能被直接访问的地址。门槛与现有入口相同（来源检查、只读、只看得到当前会话目录），
  没有口令，也不额外要什么"服务发出来的标识"：谁连得上这个端口、拼得出地址，就能读当前会话目录里的东西。
  这是有意为之，不是漏了——这台服务本来就没有口令，同网段能连上的人本来就能让 pi 读写这台机器。
