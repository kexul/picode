## 一、3b：另外三样从 stderr 搬到事件口（**已做完**，`7f73f08` + 后一笔）

派子活、后台命令、「加载了什么」现在都走事件口了：桥里 `emit()` 先看 `relayReady()`，
有中转就 `relayPost(…)`、没有才写 stderr（互斥）。后端在 `onBridgeEvent` 里分给
`onTabaRequest` / `noteBashTask` / `noteEnvSnapshot`（跟老路同一个处理，逻辑没重写）。

- **派子活验过**：`dev/relayCheck.js` 里那条（假 pi 调真扩展的 `task`）连跑三遍全过，
  中转日志里能看到 `收到桥上报的事件：taba（pi-…）`。
- **后台命令 / 「加载了什么」验不到真代码**：假 pi 里这两样是假 pi 自己往 stderr 写帧的
  （它跑不起 pi 自己的 bash API），所以那两条桥的真实代码只能在你机器上用真 pi 点一遍：
  开个会话 → 让模型跑一条长命令并「放后台」→ 跑完看清单与交回的那条消息；点开「工具」看清单。
- 四份生成的桥源码都用 TypeScript 转译过一遍（语法检查），都在、都带事件口。

下面是当初记的改法，留作参考：


现在还在 stderr 上走 base64 暗号的是三样：**派子活（taba）**、**后台命令（bash）**、
**「加载了什么」（env）**。中转的事件口已经在了（`POST /event`、`GET /reply`），
`src/relayBridgeSource.ts` 里那段客户端也已经拼进了 `askBridgeSource`，照着它改就行。

要动的地方：

- `src/bashBridgeSource.ts`、`src/envBridgeSource.ts`、`src/tabaBridgeSource.ts`：各自拼一段
  `${relayClientCode("http")}`（记得在 import 里加 `import * as http from "node:http";`），
  把现在写 stderr 的那句换成：
  ```ts
  if (relayReady()) { void relayPost("<bash|env|taba>", <幂等键>, payload); }
  else { emit(payload); }   // 没有中转才走老路，两条路互斥
  ```
  幂等键：bash 用 `<start|end>-<编号>`，env 用时间戳，taba 用它自己的请求编号。
- `src/sessionRuntime.ts` 的 `onBridgeEvent`：现在只认 `"ask"`，再加 `"bash"`（交给已有的
  `noteBashTask`）与 `"env"`（交给已有的 `noteEnvSnapshot`）。这两个方法现在是 private，改成
  供事件调用的公开/包内方法即可，处理逻辑一行都不用重写。
- **taba 要多一步**：它需要回执（受理 / 拒绝）。桥那边拿 `replyId` 长轮询等，
  后端在 `onTabaRequest` 受理（或拒绝）以后 `client.answerBridgeEvent(replyId, {ok:true, ...})`。
  注意 `PiClient.answerBridgeEvent` 已经有了，照 ask 那条路用。
- 搬完以后，`piFrames` 那套 base64 拆帧（`src/piFrames.ts` 与 `sessionRuntime` 里的
  `TABA_DECODER` / `ASK_DECODER` / `BASH_DECODER` / `ENV_DECODER`）只剩"没有中转时"的退路。
  想彻底删，就得先决定"没有中转还能不能用这几样"——现在 `PICHAT_NO_RELAY=1` 时它们照旧能用，
  这是有意的（调试、以及 relay 起不来时不至于功能全灭）。

### 这一笔怎么验（注意两条）

1. **派子活**：`dev/relayCheck.js` 里已经有一条（假 pi 会调真扩展的 `task` 工具），
   搬完照旧能过就说明对。
2. **后台命令 / 「加载了什么」**：假 pi 里这两样是**假 pi 自己往 stderr 写帧**的（它跑不起
   pi 自己的 bash API），所以搬完以后 `dev/` 那套**验不到桥的真代码**。要么
   - 在真 pi 上点一遍：开会话 → 让模型跑一条长命令并「放后台」→ 跑完看那块清单与交回的那条消息；
     再点开输入框下方那颗「工具」看清单有没有；
   - 或者给 `dev/fakePi.js` 加一条"走真 bash 桥"的戏（要模拟 pi 的 bash API，工作量大，未必值）。

## 二、收尾那一笔（进行中）

**已经做掉一件：后台命令跨重启不丢（`0f7a22f` 之后那笔）。** 中转给每只 pi 记了"事件水位"
（最后一个交给过某个后端的事件序号），换后端时按它往后补 —— 重启那一小会儿里发生的
"不用回执"的事件（后台命令跑完了、加载了什么）也会补过去。以前只重推"还没答的提问"。

验：`dev/relayCheck.js` 新加一节四之五 —— 假 pi 那边也改成走事件口（`emitBash` 先看
`PICHAT_RELAY_URL`），然后：放一条后台命令 → 重启后端 → 断言"跑完了"那条照样交回会话。
连跑三遍全过。**注**：这验到的是"事件 → 清单 / 跑完交回会话"这条后端链路；真桥那一段
（真 pi 里接管 bash 的扩展）仍然要在真 pi 上点一遍。

剩下的：

- ~~**自动模式那一轮的接续**~~（**已做**）：认回一个会话以后，如果它开着自动模式、现在闲着、
  又没有判官在跑，就照着"这一轮刚跑完"那样叫一个判官（`resumeAutoLoop`）——判官说继续就继续、

## 三、`dev/reconnect.js` 整套连着跑的 16 项失败

单个场景都过（已验 `--scene freeze`、`--scene scroll`），整套连着跑从场景三以后开始崩，
样子是"轮次没跑完就发下一句"的连锁反应。怀疑是十场共用一个后端 / 一块屏，前面的场景把
会话留在"还在跑"的状态。

**结论：整套连跑现在全部通过**（3 分 36 秒，10 个场景）。

做法：**每个场景一份干净的后端 + 一块干净的屏**（`main()` 里把 harness / 页面挪进循环）。
以前十场共用一个：前一场留在"还在跑"的会话、留在页面上的消息、留在补发账里的序号，都会串到
下一场，症状就是"某一轮没跑完就发下一句"、条数对不上这类看着像产品的假故障。

如果还不过，再按这两步查：

1. 看是不是某个场景自己依赖了"上一场留下的会话"（那种场景要自带造数据）。
2. 要确认是不是这次改动带来的：在 `bb32688`（还没有中转）那个提交上跑同一套对照。
   （试过一次：worktree + junction `node_modules` + `npm run compile` 都成，
   但 `reconnect.js` 起来就退了，没跑出结果，得再看它为什么退。）

## 四、几个已经知道的小事

- **一个真问题（要先查明）**：`dev/relayCheck.js` 里"点了以后答案交回了模型"这一条**是忽好忽坏的**
  （三次里两次没过；把窗口从 30 秒放到 90 秒也没过，所以不是"判早了"）。也就是说：
  重启之后卡片画回来了、也点得动，但**答案有时没送到 pi 那边的长轮询**。排查方向：
  1. 后端 `answerBridgeEvent` → 中转 `reply` 那一步有没有真的发出去（在中转里把 `reply` 的
     `replyId` 与收到的事件对一遍，打一行日志）；
  2. 桥那边长轮询拿到的是 `answered` 还是 `unknown` / `offline`（桥里也打一行）；
  3. 注意 `rememberEvent` 只按 `key|id` 去重、`reply` 是全表扫 `replyId`，两边如果用错了
     同一条事件（例如 restart 前那条与 restart 后重推的那条），答案会落到"另一条"上。

  **结论（一轮四遍跑下来）：这一条不是产品的毛病，是断言盯错了地方。**
  桥那边日志显示答案确实到了（`长轮询 r-375 → answered value={"picked":["A"]}`），
  而页面那边这句话有时是逐字增量、有时是随后来的历史批次，盯页面就会看走眼。
  现在改成**直接问 pi**：经中转发一条 `get_messages`，看它自己的消息树里有没有「用户选了：A」——
  四遍全过。

  **另外修掉的真 bug（`315eac5`）**：`/reply` 的长轮询以前在 `req.on("close")` 里把这条 `replyId`
  的 waiter **整组**清掉（请求体读完、连接抖一下都会走到那儿），别的还在等的轮询会一起被摘。
  改成只摘自己那一个。（桥那侧的长轮询日志也留着了：`[ask] 报题 … / [ask] 长轮询 … → answered|pending`。）

  剩下偶尔不过的是「长话」那一节的前缀断言（四遍里一遍）：日志显示是**两轮同时在这一只 pi 上吐字**
  （前一轮的尾巴和这一轮的正文交织在一起），也就是上一次发话时上一个回合还没真的收尾。
  已修（测试侧）：加了一个 `waitQuiet`——等这个会话的正文增量**连续 700 毫秒没有新的**
  再开口，不再只看会话表里的 `streaming`。改完连跑四遍全过。
- 中转十分钟没人连（后端没回来：编译挂了、终端关了）会连 pi 一起收摊，不留野进程。
- 桥接扩展的代码一变，被中转保活的那只 pi 跑的就是旧代码：认回会话时比过 `-e` 文件路径，
  对不上就杀掉重开（见 `chatHost.restoreLiveSessions`）。
