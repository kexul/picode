## 一、3b：另外三样从 stderr 搬到事件口

现在还在 stderr 上走 base64 暗号的是三样：**派子活（taba）**、**后台命令（bash）**、
**「加载了什么」（env）**。中转的事件口已经在了（`POST /event`、`GET /reply`），
`src/relayBridgeSource.ts` 里那段客户端也已经拼进了 `askBridgeSource`，照着它改就行。

要动的地方：

- `src/bashBridgeSource.ts`、`src/envBridgeSource.ts`、`src/tabaBridgeSource.ts`：各自拼一段
  `${relayClientCode("http")}`（记得在 import 里加 `import * as http from "node:http";`），
  把现在写 stderr 的那句换成：
  ```ts
  if (relayReady()) { void relayPost("<bash|env|taba>", <幂等键>, payload); }
  else { emit(payload); }   // 没有中转才走老路，两条路互斥
  ```
  幂等键：bash 用 `<start|end>-<编号>`，env 用时间戳，taba 用它自己的请求编号。
- `src/sessionRuntime.ts` 的 `onBridgeEvent`：现在只认 `"ask"`，再加 `"bash"`（交给已有的
  `noteBashTask`）与 `"env"`（交给已有的 `noteEnvSnapshot`）。这两个方法现在是 private，改成
  供事件调用的公开/包内方法即可，处理逻辑一行都不用重写。
- **taba 要多一步**：它需要回执（受理 / 拒绝）。桥那边拿 `replyId` 长轮询等，
  后端在 `onTabaRequest` 受理（或拒绝）以后 `client.answerBridgeEvent(replyId, {ok:true, ...})`。
  注意 `PiClient.answerBridgeEvent` 已经有了，照 ask 那条路用。
- 搬完以后，`piFrames` 那套 base64 拆帧（`src/piFrames.ts` 与 `sessionRuntime` 里的
  `TABA_DECODER` / `ASK_DECODER` / `BASH_DECODER` / `ENV_DECODER`）只剩"没有中转时"的退路。
  想彻底删，就得先决定"没有中转还能不能用这几样"——现在 `PICHAT_NO_RELAY=1` 时它们照旧能用，
  这是有意的（调试、以及 relay 起不来时不至于功能全灭）。

### 这一笔怎么验（注意两条）

1. **派子活**：`dev/relayCheck.js` 里已经有一条（假 pi 会调真扩展的 `task` 工具），
   搬完照旧能过就说明对。
2. **后台命令 / 「加载了什么」**：假 pi 里这两样是**假 pi 自己往 stderr 写帧**的（它跑不起
   pi 自己的 bash API），所以搬完以后 `dev/` 那套**验不到桥的真代码**。要么
   - 在真 pi 上点一遍：开会话 → 让模型跑一条长命令并「放后台」→ 跑完看那块清单与交回的那条消息；
     再点开输入框下方那颗「工具」看清单有没有；
   - 或者给 `dev/fakePi.js` 加一条"走真 bash 桥"的戏（要模拟 pi 的 bash API，工作量大，未必值）。

## 二、收尾那一笔

- **自动模式那一轮的接续**：判官是另一只 pi（已被中转保活）。它在重启窗口里跑完时，
  结果交回走的是后端内存里的 `onTurnEnd`；现在这一下会丢。要么让判官的结果走事件口（推荐，
  跟 3b 一起做），要么在认回会话时补一次"有没有刚跑完的判官"。
- **"点开全文 / 大图"重启后取不到了**：`omittedText` / `omittedImages` 是后端内存表。
  改成点开时回 pi 现取（`get_messages` 里那份还在），或者让中转也存一份。
- **后台命令清单**（可选）：现在靠 `start` / `end` 事件累积。要"重启后界面立刻就有"，得让中转
  也记一份每个会话的后台命令清单，认回会话时交给新后端。

## 三、`dev/reconnect.js` 整套连着跑的 16 项失败

单个场景都过（已验 `--scene freeze`、`--scene scroll`），整套连着跑从场景三以后开始崩，
样子是"轮次没跑完就发下一句"的连锁反应。怀疑是十场共用一个后端 / 一块屏，前面的场景把
会话留在"还在跑"的状态。

查法：

1. 先给每个场景一份干净的 harness（现在 `main()` 里只建一次）——如果这样就全过，
   那就是场景之间互相干扰，改测试脚本的排队方式即可，跟产品无关。
2. 要确认是不是这次改动带来的：在 `bb32688`（还没有中转）那个提交上跑同一套对照。
   （试过一次：worktree + junction `node_modules` + `npm run compile` 都成，
   但 `reconnect.js` 起来就退了，没跑出结果，得再看它为什么退。）

## 四、几个已经知道的小事

- `dev/relayCheck.js` 里"点了以后答案交回了模型"偶尔会超时一次（假 pi 的节奏 + 30 秒窗口），
  重跑就过。以后可以改成"等到这一轮落盘"再断言，别用固定窗口。
- 中转十分钟没人连（后端没回来：编译挂了、终端关了）会连 pi 一起收摊，不留野进程。
- 桥接扩展的代码一变，被中转保活的那只 pi 跑的就是旧代码：认回会话时比过 `-e` 文件路径，
  对不上就杀掉重开（见 `chatHost.restoreLiveSessions`）。
